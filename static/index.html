Visual Dataflow & Execution Models

1. Sequential Architecture

Linear One-by-One Pipeline · Serialized Execution Chain
Strict Serial Pipeline Single Thread (Concurrency = 1)
💡
How It Works: Agents execute strictly one after another in a deterministic linear chain. No two agents execute simultaneously. Each agent waits for the preceding agent to finish its retrieval and write to the shared Blackboard before it can start. If evidence is insufficient, it triggers a linear re-plan loop back to Orchestrator (max 2 rounds).
INPUT
❓ User Question
Natural language architectural query ingested into the pipeline
➔ Step 1 starts
STEP 1 · PLANNING
🧠 Orchestrator Agent
Deconstructs question and prescribes fixed one-by-one execution order: Code ➔ History ➔ Issue/PR
Single thread: Planned execution list created
➔ Code Agent executes (Other agents wait)
STEP 2 · 1ST RETRIEVER
💻 Code Analysis Agent
Scans active AST, source files, and kernel paging headers
● Running (1/3) — History RAG & Issue/PR must wait
➔ Code Agent finishes · History Agent starts
STEP 3 · 2ND RETRIEVER
📜 Git History RAG Agent
Executes only after Code Agent finishes. Retrieves commit history and author diffs
● Running (2/3) — Issue/PR agent still waiting
➔ History Agent finishes · Issue/PR starts
STEP 4 · 3RD RETRIEVER
🪲 Issue & PR Extractor
Executes 3rd in line. Pulls pull requests, bug discussions, and review threads
● Running (3/3) — All serial retrievals now complete
➔ Writes accumulated evidence
STEP 5 · SHARED STATE
📋 Shared Blackboard (Sequential Accumulator)
Holds linearly appended evidence chunks collected in strict FIFO arrival order
➔ Pass to gatekeeper
STEP 6 · SUFFICIENCY GATE
🛡️ Verifier Agent (Cross-Validation)
Evaluates Chain-of-Thought validity, citation ground truth, and evidence sufficiency
🔄 Conditional Re-Plan Loop: If evidence < 3 chunks or confidence < 0.6, loops back to Step 1 (Max 2 rounds)
➔ Evidence approved
STEP 7 · SYNTHESIS
✍️ Reviewer Agent
Synthesizes verified evidence into final multi-source architectural report
➔ Final output
OUTPUT
🎯 Verified Architectural Answer
Delivered to user with citations and complete execution audit trail
Control Topology
Linear Directed Chain
Unidirectional pipeline handoff from Step 1 to Step 7
Concurrency Strategy
Single-Threaded Serial
Strictly one agent active at any given moment
Memory & State
FIFO Blackboard Accumulator
Each agent reads previous outputs and appends its findings
Key Trade-off
High Predictability · Serial Delay
Easy to debug & deterministic, but agents cannot run in parallel

2. Hierarchical Architecture

Central Controller Pattern · Multi-Threaded Worker Pool
Master-Worker Pattern Parallel ThreadPool (3 Concurrent Workers)
💡
How It Works: A centralized Master Controller (Orchestrator) manages worker subtasks. Instead of waiting one-by-one, the controller dispatches all 3 retrieval agents concurrently in parallel using a ThreadPoolExecutor. All 3 workers write simultaneously into a thread-safe Blackboard. The Master Controller waits for barrier synchronization before routing to Verifier and Reviewer.
INPUT
❓ User Question
Question arrives at the Central Controller
➔ Controller ingests question
CENTRAL MASTER CONTROLLER
👑 Orchestrator Agent (Master Controller)
Decomposes question into 3 independent sub-tasks and assigns them concurrently into the thread pool
⚡ Concurrently Spawns 3 Worker Threads
⚡ PARALLEL THREAD POOL DISPATCH — All 3 Workers Run Simultaneously
THREAD 1 · PARALLEL
💻 Code Analysis Agent
Scans source AST & headers in Worker Thread 1
Parallel Thread #1
THREAD 2 · PARALLEL
📜 Git History RAG Agent
Searches commit logs & diffs in Worker Thread 2
Parallel Thread #2
THREAD 3 · PARALLEL
🪲 Issue & PR Extractor
Pulls GitHub discussions in Worker Thread 3
Parallel Thread #3
▼ Concurrent write into thread-safe Blackboard
THREAD-SAFE SHARED MEMORY
📋 Thread-Safe Shared Blackboard (Mutex Lock)
Protected by mutex lock to allow simultaneous safe writes from all 3 concurrent worker threads
🔒 Barrier Synchronization: Master Controller waits until all 3 threads resolve
➔ Controller routes to Quality Gate
CONTROLLER QUALITY GATE
🛡️ Verifier Agent (Cross-Validation)
Controller submits pooled evidence for validation. If gaps found, Controller re-dispatches targeted worker
🔄 Controller Re-Dispatch: Master triggers additional targeted worker thread if evidence is incomplete
➔ Controller triggers Reviewer
ANSWER SYNTHESIS
✍️ Reviewer Agent
Synthesizes multi-threaded findings into final structured response under Controller supervision
➔ Final output delivered
OUTPUT
🎯 Verified Architectural Answer
Consolidated multi-agent architectural intelligence returned to user
Control Topology
Star / Master-Worker
Central controller commands all subordinate workers
Concurrency Strategy
Multi-Threaded Pool
Concurrent worker threads execute simultaneously
Memory & State
Thread-Safe Blackboard
Thread-safe concurrent data aggregation protected by lock
Key Trade-off
High Parallel Throughput
Faster execution via parallel retrieval; requires thread locking

3. Event-Driven Architecture

Reactive Event Bus · Decoupled Pub/Sub Agent Mesh
InProcessEventBus Decoupled Reactive Topics
💡
How It Works: Agents have zero direct references to one another. Communication occurs exclusively by publishing and subscribing to typed event topics on a central InProcessEventBus. When an event fires (e.g. plan_ready), all subscribed workers react autonomously and concurrently without any direct invocation.
📢 Topic: 'question_received'
🌐 Gateway publishes question_received
Orchestrator Agent is subscribed to this topic and wakes up
⚡ IN-PROCESS EVENT BUS (InProcessEventBus) — Decoupled Pub/Sub Channel
🧠 Orchestrator Agent (Publisher)
Formulates retrieval plan and publishes plan_ready event to the bus
📢 Topic: 'plan_ready' (Broadcast)
SUBSCRIBER 1
💻 Code Analysis Agent
Reacts to plan_ready ➔ Fetches AST code ➔ Publishes evidence_posted
SUBSCRIBER 2
📜 Git History RAG Agent
Reacts to plan_ready ➔ Fetches commit logs ➔ Publishes evidence_posted
SUBSCRIBER 3
🪲 Issue & PR Extractor
Reacts to plan_ready ➔ Fetches GitHub threads ➔ Publishes evidence_posted
📢 Topic: 'evidence_posted'
📋 Blackboard Subscriber
Listens to evidence_posted events, gathers chunks, and emits evidence_ready once all workers post
🛡️ Verifier Agent (Consumer & Publisher)
Consumes evidence_ready. If insufficient, emits evidence_insufficient (triggers retry event). If approved, emits evidence_approved
📢 Topic: 'evidence_approved'
✍️ Reviewer Agent (Subscriber)
Consumes evidence_approved, synthesizes verified report, and publishes answer_complete
📢 Topic: 'answer_complete' ➔ Delivered
Control Topology
Decoupled Pub/Sub Mesh
Event bus handles all routing; zero direct agent references
Concurrency Strategy
Reactive Asynchronous
Subscribers fire concurrently when event topics trigger
Fault Isolation
Complete Boundary Isolation
A failure in one agent doesn't crash other subscribers
Key Trade-off
Maximum Extensibility
New agents can subscribe to topics without touching core engine

4. Workflow-Based (DAG) Architecture

Formal State Machine DAG · Fork/Join Barriers & Conditional Edges
State Machine DAG Fork / Join Barrier Nodes
💡
How It Works: The execution is modeled as a formal Directed Acyclic Graph state machine. The graph features explicit Fork Barrier nodes that branch state into concurrent worker nodes, and a Join Barrier node that aggregates outputs. Re-retrieval is executed via a Conditional Graph Edge that loops back to retrieval only if evidence is insufficient and round count < 2.
GRAPH STATE: START
🟢 State Machine Start
Initializes execution state dictionary: {question, round: 1, max_rounds: 2}
➔ Transition Edge: start ➔ plan_node
DAG NODE 1 · PLANNER
🧠 Orchestrator Node
Analyzes state dictionary, establishes domain targets, and emits graph execution token
➔ Transition Edge: plan_node ➔ fork_barrier
GRAPH BARRIER: FORK
🔀 Parallel Fork Barrier Node
Splits the single state graph token into 3 concurrent parallel execution branch edges
BRANCH NODE A
💻 Code Analysis Node
Executes code parsing branch; returns AST evidence dictionary
BRANCH NODE B
📜 Git History RAG Node
Executes git log branch; returns commit history dictionary
BRANCH NODE C
🪲 Issue & PR Node
Executes GitHub discussions branch; returns PR evidence dictionary
▼ Transition Edges: Branches converge into Join Barrier
GRAPH BARRIER: JOIN
🔗 Synchronization Join Barrier Node
Synchronizes all 3 branch states; merges evidence arrays into unified immutable state
➔ Transition Edge: join_barrier ➔ verify_node
DAG NODE 3 · VERIFICATION GATE
🛡️ Verification Node
Evaluates evidence confidence, completeness, and factual grounding
🔀 Conditional Graph Edge: IF (confidence < 0.6) AND (round < 2) ➔ Cycles back to Fork Barrier with refined sub-queries.
ELSE ➔ Transitions forward to Reviewer Node.
➔ Transition Edge: verify_node ➔ reviewer_node
DAG NODE 4 · SYNTHESIS
✍️ Reviewer Node
Synthesizes consolidated verified state into final architectural intelligence
➔ Transition Edge: reviewer_node ➔ END
GRAPH STATE: END
🏁 State Machine Terminal (END)
Final architectural response successfully constructed and emitted

Concurrency Strategy
Fork/Join Synchronization

State Management
Immutable State Graph Token
Each node transforms and returns a strictly typed state object
Cycle Control
Bounded Conditional Edge
Explicit edge conditions guard against non-terminating loops
